## Notes

**Workflow facts (45 lines, read in full):**
- Triggers (lines 3-8): `push` and `pull_request` to `main`, plus `workflow_dispatch`. No `pull_request_target`, no secrets. Fork PRs cannot pick up `RXET_LOCAL_CAS_SERVER` secrets because none are used.
- Matrix (line 17): `os: [ubuntu-latest, macos-latest, windows-latest]`, so one job covers all three OS. No per-OS jobs are needed.
- `dtolnay/rust-toolchain@stable` step: lines 35-36. This is the anchor for the new steps.
- `Build package` step: lines 38-39 (`R CMD build .`).
- `R CMD check` step: lines 41-45. Line 42 is `shell: bash`, lines 43-44 are the `env:` block (`_R_CHECK_FORCE_SUGGESTS: false`), line 45 is `run`. None of these change.

**Binary path per OS:**
- ubuntu and macos: `$HOME/.cargo/bin/local_cas_server`.
- windows: `$HOME/.cargo/bin/local_cas_server.exe` under bash (Git Bash, so `$HOME` is `/c/Users/...`).
- One bash step picks the suffix from `$RUNNER_OS`. No separate `if:` per OS is needed.

**Placement:** the cache restore goes before the install. The rustc-version step goes first because the cache key needs it. Order: toolchain (36) → rustc version → cache → install (with `$GITHUB_ENV` export) → Build (38) → Check (41). The install must run before the check, and this order satisfies that.

**Export mechanism:** `$GITHUB_ENV` is used, not an `env:` key on the check step. That keeps the check step unchanged (spec item 3), and the variable reaches the `R CMD check` process.

**Risks:**
- Cache key: the `rustc -V` output is needed for the key. Without a version step, the key would not track the toolchain.
- Cache hit path: a cache hit skips `cargo install` entirely. A miss compiles the server, which is slow (H2). The 45-minute timeout bounds it.
- Windows compile (H1): axum, redb, and related crates may fail or exceed 45 minutes. In that case the job fails and the Windows suite cannot run. Per STOP-and-report, do not add `continue-on-error` or skip silently.
- Windows path format: `$HOME` under Git Bash is a POSIX path (`/c/Users/...`). R on Windows may not resolve it. See Question 1.
- Windows `~` in `actions/cache` paths: the `~` expansion is assumed to work on all three runners. This is not verified locally. The first CI run will show it. If it fails, use explicit `$HOME`-based paths from a bash step.
- Local verification is limited to YAML parse and grep. CI cannot run locally. Install, cache, Windows compile, and the check run are all deferred until push.
