**Risks:**
1. **Blackhole with retries.** `serverSocket()` completes TCP handshakes via the kernel backlog but never accepts or replies, so each attempt times out after the read timeout. With default retries (5 attempts, 3 s base, growing delays), a single blackhole download can take minutes, so the 60 s bound (test 3, test 5) fails. Retries apply to transient request errors. Whether a read timeout and a connection refusal are both classed as transient is not verified in this task.
2. **Closed port with retries.** Connection refused is likely retried too, so test 1, test 2, test 4 can also be slow under defaults (estimated > 60 s, not measured). Lowering `HF_XET_CLIENT_RETRY_MAX_ATTEMPTS` to `"1"` for the test process is the proposed fix; it changes test-run config only, not product behavior, but it is a test-seam change and needs approval (see Questions).
3. **Timeout unit.** `"2"` fails humantime parsing, so a wrong value would silently keep the 300 s default, which would hang the blackhole tests for minutes. Use `"2s"` and confirm in the timing run that blackhole tests finish near the configured value.
4. **Config read timing.** The env vars must be set before `xet_client_new()` (client config read at build). Each blackhole/closed-port test creates its own client inside `with_lifecycle_env`.
5. **Port races.** A random port in 20000–40000 may be taken between probe and bind. `closed_port()` only probes for listeners; a test that finds the port reused could hang or pass for the wrong reason. Accepted residual risk; the probe retries on any listener.
6. **Temp-file residue on Windows.** Not run here (H4). Tests assume POSIX `file.rename`.
7. **Env var restore.** Restoring via `on.exit` must unset variables that were previously unset (use `Sys.unsetenv`), not set them to `""`.

## Questions

1. The spec's `HF_XET_CLIENT_READ_TIMEOUT = "2"` is invalid humantime. May I use `"2s"`? (Proposed: yes.)
2. Under default retries, the 60 s bound is likely unreachable for blackhole and possibly closed-port tests. May I set `HF_XET_CLIENT_RETRY_MAX_ATTEMPTS = "1"` in the test-only env helper (restored afterwards)? This is a test-config change, not a timeout raise, but it is a seam beyond the spec. If not approved, tests 1, 2, 3, 5 may need to be marked skip-on-slow or the spec's bound revised.
3. Should test 5 assert the error message shape (e.g., `"timed out|timeout"`) or only that an error occurs? Proposed: only that an error occurs, since hf-xet's message text is not stable.
