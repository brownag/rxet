## Notes
**Path under test: term fetch 401 (not the reconstruction).** The reconstruction is always fetched first. A 401 there would fail the call before the term fetch runs, so it would not test the term-fetch path that 6.2.1 exercises. The fault server keeps `/v2` (404) and `/v1/reconstructions` (JSON) as in 6.2.1 and returns 401 only on `/xorb/`. A reconstruction 401 is a possible second case, left out of this task.

**Why 401 is fatal and not retried.** `remote_client.rs:600` sets `.with_retry_on_403()` on the term fetch. Only 403 is retried (`retry_wrapper.rs:201-204`). `retry_wrapper.rs:499-520` classifies other 4xx as Fatal, and `retry_wrapper.rs:211` wraps it as `process_error("Fatal Error", e, false)`. `remote_client.rs:634-639` refreshes the signed URL only on 403. So a 401 should give one request and a fast error, with no retry loop and no URL refresh.

**Expected error text (source-derived, not yet run).** The 401 error comes from `error_for_status()` on the response (`retry_wrapper.rs:198`), before the body is read. The text should be `Fatal Error: <api tag> api call failed: HTTP status client error (401 Unauthorized) for url (http://127.0.0.1:<PORT>/xorb/term)`, wrapped by the download and stream layers (for example `finish error: Task error: ...`). The reqwest Display format is standard, but it is unverified here. The run records the real text.

**Risk: decoder error instead of 401.** The status check runs before the body is read, so a decoder error should not appear. If the server sends a body or the headers are malformed, the text can change to `error decoding response body`, as in 6.2.1. The `expect_match(msg, "401")` assertion is what catches this.

**Token canary.** `reqwest` errors show the status and URL, not request headers, so the bearer token should never appear in the message. The canary check is a regression guard, not proof that the token is never logged. The URL contains only the loopback port and path, not the token.

**Helper edit (only change to a shared file).** The existing helper always returns 200 from `/xorb/`. A 401 needs a status argument on the server. The edit is additive with a default of 200, so 6.2.1 is unchanged. It is recorded in STATE_6.md and tested by re-running `fault-midstream`.

**Hygiene pattern.** The existing `tempfile("hf_home_")` string in `test-fault-midstream.R` contains `hf_`. A bare `grep -n hf_` will hit it, so the check uses the token-shaped pattern `hf_[A-Za-z0-9]{20,}` instead.

**Timing.** No waiting for expiry (J2). 6.2.1 took about 2-3 s per call. The 401 path should be faster because it has no short-read retry. The 60 s bound is an assertion, not a timeout to widen (H6).
