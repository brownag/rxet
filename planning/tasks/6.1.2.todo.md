## Notes
- **Location: Rust (`src/rust/src/lib.rs`), not R.** The Rust side already holds the expected size (`size`, from `to_whole_bytes`) and the wrapped error text. The R wrapper (`R/download.R:30-57`) only sees the final string, so mapping there would mean parsing the message in R, which is the same string match with more moving parts. The R file stays untouched.
- **Why not a typed check.** hf-xet 1.7.0 converts `SizeMismatch` to `XetError::Internal` (`hf-xet-1.7.0/src/error.rs:248-250`, displayed at `:94-95`), so there is no typed variant to match. A typed pre-check would need a second read of the file or a crate change, and no new dependencies are allowed.
- **How the message is produced.** The xet-data check (`xet-data-1.7.0/src/processing/file_download_session.rs:364-368, 414-418`) yields `File size mismatch: expected N bytes but downloaded M bytes`. hf-xet wraps it as `Internal error: ...`. The existing mapping at lib.rs:266 yields `download error: Internal error: File size mismatch: expected 65537 bytes but downloaded 65536 bytes`. The new helper takes `expected` from `size` (not from the text), parses only `M` from the text, and builds the plain message. The `finish error:` mapping (lib.rs:270) is left as is; the size check runs in the download call per 6.1.1.
- **Behaviour kept.** `safe_exec` (lib.rs:31-44) still catches panics, the `.part` cleanup (`R/download.R:49`) is unchanged, and no destination file is written.
- **Risks.** (1) The match string `File size mismatch` and the `downloaded ` token come from xet-data 1.7.0; they are pinned by `src/rust/Cargo.lock` but would break silently on an hf-xet upgrade. The unit test and the R test both catch that, so a bump must re-run both. (2) If the mismatch surfaces at `finish_blocking` instead of the download call, the message keeps the `download`/`finish` prefix logic: the helper must be applied to both mappings or the test will show it. (3) Number formatting: `size` is u64, so no scientific notation.

## Questions
1. The plain message drops the `download error:` prefix for this case only. Is that acceptable, or should it keep the prefix (`download error: downloaded size does not match ...`)?
2. Parsing the downloaded count from the message is the only option without a crate change. Is that accepted, given the risk noted above?
